# civil-code-rag

**《中华人民共和国民法典》RAG 问答与检索评测闭环** — 1260 条法律条文上的切分策略 × 重排对比实验，带低置信拒答与引用校验。检索与评测**完全本地运行，不需要任何 LLM API key**。


## 它解决什么问题

法律问答是 RAG 最典型的企业落地场景之一（法务咨询、合同审查、合规检索）。本项目在一部结构完整、事实密集的真实法律文本上回答三个工程问题：

1. **切分策略对检索质量影响多大？** 结构盲滑窗 vs 按条文切分 vs 句嵌入语义切分；
2. **重排（cross-encoder rerank）在什么情况下有收益？**
3. **拒答阈值怎么定才不是拍脑袋？** 用域外问题的分数分布做校准。

## 结果（56 题 golden 集，条文级指标，n=50 域内题）

| 切分策略 | 重排 | hit@5 | MRR@5 | recall@5 |
|---|:---:|---:|---:|---:|
| fixed 滑窗 256 字（结构盲） | ✗ | 0.920 | 0.725 | 0.913 |
| fixed 滑窗 256 字（结构盲） | ✓ | 0.980 | 0.940 | 0.980 |
| article 按条文 | ✗ | 0.960 | 0.852 | 0.943 |
| article 按条文 | ✓ | 0.980 | 0.950 | 0.973 |
| **semantic 语义切分** | ✗ | **1.000** | 0.912 | 0.993 |
| **semantic 语义切分** | ✓ | **1.000** | **0.977** | **0.997** |

切分产物统计：fixed 467 块（均值 256 字）/ article 1260 块（115 字）/ semantic 1001 块（137 字）。

**拒答校准**：语义切分阈值 0.718（条文内相邻句相似度中位 0.741，跨条文 0.695，取中点）；拒答阈值 τ=0.96（域内 top-1 重排分数第 5 百分位）——域内中位 0.999，域外中位 0.050，**域外 6 题误接受 0 题**。

完整数据：`results/metrics.csv`、`results/calibration.json`、失败案例 `results/failures.md`。

### 怎么读这些数字（有一个反直觉的结果）

- **直觉说"按条文切分应该最强"——数据说不是。** 语义切分在不用重排时 hit@5 已到 100%，重排后 MRR 0.977 全场最优。原因：语义切分会把**主题相关的相邻条文合并进同一块**（比如"遗嘱的六种形式"对应第一千一百三十四至一千一百三十九条，语义切分把它们聚在一起），一次检索同时覆盖多条 golden 条文、且块内信号更集中；按条文切分的块只有 115 字，单条孤立，主题型问题要靠多条各自上榜。域内题里有一题（Q045 遗嘱形式）golden 覆盖 6 条，正好放大了这个差异。
- **语义切分赢检索指标，但不是没有代价**：它的块跨条文边界，"答案由哪一条支撑"的引用粒度变模糊；对法律问答这种引用即交付物的场景，按条文 + 重排（hit@5 0.98 / MRR 0.95）引用单元干净。加上构建成本（见下），实用建议：**引用敏感场景用 article + rerank，纯检索问答用 semantic + rerank**。
- **重排是全场性价比最高的一步**：MRR 提升从 +0.06（semantic）到 +0.22（fixed），越弱的基线受益越大；它修的主要是排序位置而不是召回。
- **结构盲基线真正伤的是排序位置**：fixed 不重排时 hit@5 0.92 但 MRR 只有 0.725——正确条文在池子里（recall@20 = 0.98）但排不到前面，滑窗把条文拦腰切断后，含答案的那半个条文与问题的相似度被稀释了。
- **失败案例值得看**：fixed 不重排有 4 题 top-5 未命中，其中 Q011（表见代理）在所有配置的 top-20 里都不出现——问题问"什么条件下代理行为有效"，而条文写"相对人有理由相信行为人有代理权的"，这是**稠密检索的改写鸿沟**，靠切分和重排都救不了，得靠查询改写或同义扩展。
- **拒答阈值的分离度大得意外**：域内 / 域外的 top-1 重排分数中位数相差 0.95（0.999 vs 0.050），τ 取域内第 5 百分位后域外零误接受。注意域外题只有 6 道，这个 0% 只是"在 6 道上没错过"，不是泛化结论。
- **成本披露**：语义切分要对全库 ~8600 句逐句嵌入，构建耗时 4524s（CPU），约为按条文切分（199s）的 23 倍；如果索引需要日更，这个成本要先进预算。

### 这套指标的一个已知偏向（先说清楚）

命中规则是「chunk 覆盖的**任意一条**条文是 golden 就算命中」，recall 也按 chunk 覆盖条文的并集算。语义切分的块平均 137 字、上限 384 字，比 fixed 的 256 字窗口更大，而且天然跨条文边界——所以它比另外两种策略更容易「擦边命中」。上面把 semantic 领先解释成「主题聚合」，那只是一部分原因，另一部分可能来自指标宽松本身。

三个策略的块大小上限也不一致（fixed 256 / article 512 / semantic 384），严格说不是完全受控的对比。

如果重做，会补两个更严的口径：① 只有「chunk 覆盖的条文**全部**属于 golden」才算命中；② 按覆盖条文数做 precision 惩罚。这两项目前没实现，所以上表的差距应当读作**上界**，不是精确效应量。

另外，`calibration.json` 里的分数是 cross-encoder 的 **sigmoid 概率**（sentence-transformers 对单标签重排模型默认套 sigmoid），不是 raw logit——τ=0.96 是概率阈值。

还有一点要说清楚：拒答阈值 τ 是在**评测用的那 50 道域内题**的 top-1 分数分布上取的第 5 百分位，然后又在同一批题上报告结果——严格说这是 in-sample 阈值，域内误拒率被这个选择隐式优化过。干净的做法是把域内题分 train / held-out 两半，或另取一批题定阈值。域外误接受率不受影响（域外题没参与定阈值，只用于报告）。

## 复现

```bash
# 1. 环境（Python 3.11+）
uv venv && uv pip install -e ".[dev,embed,llm]"

# 2. 语料（仓库已含解析好的 data/corpus/civil_code_2020.json 与原始 PDF；
#    想从头解析：python scripts/build_corpus.py）

# 3. 校验评测集（CI 也会跑）
python scripts/validate_qa.py

# 4. 跑评测网格（首次运行自动从 HuggingFace 下载 bge 模型，约 1.2 GB；
#    若 hub 下载卡住，用 bash scripts/download_models.sh 走 curl 断点续传）
export HF_HOME=./data/models/hf     # Windows: set HF_HOME=...
python scripts/run_eval.py

# 5. 提问（无 key = 检索模式；有 key = 生成模式）
python -m civil_code_rag.cli "诉讼时效期间是几年"
CCR_LLM_API_KEY=sk-... CCR_LLM_BASE_URL=https://api.deepseek.com ccr-ask "诉讼时效是几年"
```

> 注意用词：法条里没有的词（比如口语的「离婚冷静期」，第一千零七十七条只写「三十日」）会让重排分数掉到 τ 以下而被拒答——这正是 Q011 那类改写鸿沟在拒答层的表现。提问尽量贴近法条用语。

## 架构

```
PDF（人大官网打印版）→ 行级解析器 → 1260 条 Article（编/分编/章/节/条层级）
        │                                  ↑ 断言：条文号 1..1260 严格连续
        ▼
三种切分 ── fixed：256 字滑窗（结构盲基线）
        ├── article：按条文 + 层级标题前缀（结构感知）
        └── semantic：bge 句嵌入，相邻句相似度 < 阈值处断开
        │            （阈值由语料统计校准：条文内 vs 跨条文相邻句相似度中位数的中点）
        ▼
bge-small-zh-v1.5 嵌入 → Chroma / numpy 双后端检索 → top-20
        ▼
bge-reranker-base 重排 → top-5 → 条文级 hit@5 / MRR@5 / recall@5
        ▼
生成（可选，OpenAI 兼容）：强制引用条文号 + 引用来源校验；top-1 分数 < 阈值 → 拒答
```

## 评测方法学

- **golden 集机器校验**：50 道域内题的判定条文与答案关键词由 `scripts/validate_qa.py` 逐字校验（CI 强制），评测集本身不会静默出错；另 6 道域外题用于拒答校准。
- **指标在条文级计算**：三种切分的 chunk 粒度不同，只有把命中判定统一到条文号上才可横向对比。
- **两个校准都不接触测试答案**：语义切分阈值只用语料的相邻句相似度分布；拒答阈值只用域内问题的 top-1 分数分布（第 5 百分位），然后**在域外题上报告**误接受率。
- **指标不依赖 LLM**：hit@k / MRR@k / recall@k 只依赖嵌入与重排模型，本地可复现。生成质量维度的 LLM-as-judge（faithfulness / relevance）已实现（`civil_code_rag/judge.py`），需要 API key，属于可选层。


## 贡献边界

- RAG 流程的参照对象：LlamaIndex / LangChain 官方入门示例的通用模式（chunk → embed → retrieve → generate）。**本项目没有使用 RAG 框架**，管道从零实现（依赖仅 numpy / chromadb / sentence-transformers），因为对比切分策略必须自己控制每个环节。
- 语料：《中华人民共和国民法典》全文，来自全国人大官网打印版 PDF（FAOLEX 镜像，`data/raw/civil_code_fao.pdf`）。依据《著作权法》第五条，法律法规不适用著作权保护；来源已在 README 与语料 JSON meta 中标注。
- 模型：BAAI/bge-small-zh-v1.5 与 BAAI/bge-reranker-base，MIT/Apache 许可，HuggingFace 下载。
- 解析器、三种切分、56 题评测集、指标实现、拒答与引用校验、全部测试：本人完成。

## 已知局限

- 评测集 56 题、单一法律文本——结论方向可信，具体数字不可外推到其他领域语料；
- 三种切分的块大小上限不一致（fixed 256 / article 512 / semantic 384），且「覆盖任意一条即命中」的规则偏向跨条文的大块——见上文「这套指标的一个已知偏向」，差距应读作上界；
- 语义切分阈值校准用了语料前 4000 句的样本统计，非全量（速度权衡）；
- 生成与 LLM-as-judge 层未在无 key 环境跑通端到端（代码与单测就绪，接 key 即跑）；
- `semantic` 切分对全部 ~8k 句子逐句嵌入，构建耗时约为按条文切分的 23 倍（4524s vs 199s，CPU）。
